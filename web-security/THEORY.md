# Теория

Основы для чтения HTTP-запросов и разбора результатов проверок. Записи выполненных действий собраны в [практике](PRACTICE.md).

## HTTP: запрос и ответ

Когда пользователь открывает страницу или отправляет форму, браузер обращается к серверу. Он отправляет **запрос**, а сервер возвращает **ответ**: например, страницу, данные о товаре или сообщение об ошибке. Правила такого обмена задаёт HTTP.

HTTPS защищает передачу этих сообщений с помощью TLS. Ошибки в обработке запросов всё равно могут оставаться в самом приложении.

### Как читать запрос

Учебный пример отправки комментария в текстовом представлении Burp. Домен `blog.example` и путь `/example/comment` условные; `<SESSION_ID>` заменяет настоящий идентификатор сессии.

```http
POST /example/comment HTTP/2
Host: blog.example
Cookie: session=<SESSION_ID>
Content-Type: application/x-www-form-urlencoded
Content-Length: 56

postId=4&comment=3&name=dd&email=dd%40gmail.com&website=
```

| Часть запроса | Что она означает |
| --- | --- |
| `POST` | Метод: данные отправляются серверу для обработки. Здесь это поля формы комментария. |
| `/example/comment` | Путь к ресурсу или обработчику после метода. |
| `HTTP/2` | Версия протокола HTTP. Позволяет вести несколько обменов одновременно в одном соединении. |
| `Host: blog.example` | Домен сервера. |
| `Cookie: session=<SESSION_ID>` | Заголовок с идентификатором сессии. |
| `Content-Type: application/x-www-form-urlencoded` | Формат тела: поля формы в виде `имя=значение`, разделённые символом `&`. |
| `Content-Length: 56` | Размер тела в байтах. |

- В текстовом представлении Burp тело начинается после пустой строки. `Cookie` находится в заголовках, а не в теле.
- Некоторые символы в теле закодированы. Например, `%40` означает `@`.
- Burp показывает HTTP/2 в удобном текстовом виде, похожем на HTTP/1. По сети HTTP/2 передаёт сообщения в двоичном формате.

Разбор тела из занятия:

- `postId=4` — идентификатор поста: `4`.
- `comment=3` — текст комментария: «3».
- `name=dd` — указанное имя: `dd`.
- `email=dd%40gmail.com` — адрес почты: `dd@gmail.com`.
- `website=` — поле передано пустым.

`GET` обычно используют для получения данных, а `POST` — для отправки данных на обработку. Сам по себе выбор метода ещё ничего не говорит о наличии уязвимости.

### Как читать ответ

Ответ находится отдельно, в панели **Response**. У него свои **статус**, **заголовки** и **тело**.

- Статус сообщает, как сервер оценил запрос; тело содержит возвращённые данные.
- `200 OK` — успешная обработка запроса.
- `302 Found` — перенаправление; адрес перехода указан в заголовке `Location`.
- `403 Forbidden` — сервер отказывает в выполнении запроса.

Код ответа сам по себе не доказывает нужное изменение. Нужно проверить результат на сайте: появился ли комментарий или сохранилась ли новая почта после обновления профиля.

## Cookie и сессия

**Cookie** — небольшая пара «имя=значение», которую браузер хранит и отправляет в подходящих запросах. Она может хранить, например, настройку языка или идентификатор сессии.

**Сессия** позволяет приложению связывать несколько запросов с одним пользователем. В распространённой схеме сервер хранит данные сессии у себя, а браузеру выдаёт её идентификатор через cookie.

Это работает так:

1. Пользователь входит в аккаунт.
2. Сервер связывает сессию с аккаунтом и отправляет браузеру cookie с её идентификатором.
3. При следующих подходящих запросах браузер прикладывает эту cookie, в том числе при переходах между страницами.
4. Сервер проверяет идентификатор и находит соответствующую сессию.

| Заголовок | Кто отправляет | Для чего |
| --- | --- | --- |
| `Set-Cookie` | Сервер → браузер | Предлагает сохранить или обновить cookie. |
| `Cookie` | Браузер → сервер | Передаёт сохранённые cookies с запросом. |

В записи `session=<SESSION_ID>` слово `session` — имя cookie, а после `=` находится идентификатор сессии. `<SESSION_ID>` — учебная замена настоящего значения.

Идентификатор сессии — отдельное значение: он не равен паролю или CSRF-токену. Cookie может существовать и до входа в аккаунт. Сервер может её обновлять; новый визит не обязательно означает новый идентификатор.

Действующий украденный идентификатор может позволить воспользоваться чужой сессией. Это захват сессии.

## Зачем нужен Repeater

- В **Proxy → HTTP history** находится уже отправленный браузером запрос и полученный ответ.
- **Send to Repeater** копирует запрос в редактор. Само копирование не отправляет его заново.
- Кнопка **Send** отправляет запрос серверу ещё раз.
- **Response** в Repeater показывает ответ именно на новую отправку.
- Сначала можно повторить запрос без изменений. Затем изменить один параметр и сравнить ответ и результат на сайте.
- Так можно отправить комментарий без повторного заполнения формы. Если сервер примет повторный запрос, может появиться ещё один комментарий.

## SSRF: запрос выполняет сервер

**SSRF (Server-Side Request Forgery)** — ошибка, позволяющая через приложение заставить сервер обратиться к ресурсу, обращения к которому эта функция не должна допускать.

Для примера возьмём магазин с проверкой наличия товара:

1. Браузер спрашивает магазин, сколько товара осталось.
2. Сервер магазина обращается к сервису склада.
3. Сервер получает остаток и возвращает его браузеру.

Само обращение к складу — обычная работа функции. Проблема возникает, если через входные данные можно направить сервер к непредусмотренному ресурсу.

- У сервера может быть доступ к внутренним сервисам, недоступным пользователю напрямую.
- SSRF может позволить раскрыть данные или выполнить нежелательные действия от имени сервера.
- Возможность прочитать закрытые данные зависит от конкретной уязвимости.

### Что нужно подтвердить

Для вывода о SSRF нужно показать, что ввод пользователя вызвал непредусмотренное обращение сервера. Наличие URL в параметре или ответ `200 OK` этого не доказывает. Выбор другого разрешённого склада тоже может быть нормальной работой магазина.

### Для чего нужен allowlist

**Allowlist** — список разрешённых направлений запросов. Например, функция проверки товара должна обращаться только к известным складам.

- Нужно проверять адрес назначения и разрешённый протокол.
- Нужно учитывать перенаправления: разрешённый адрес может перенаправить на запрещённый ресурс. Автоматические переходы можно отключить; если они нужны, каждое новое назначение тоже проверяют.
- Дополнительно сетевые правила могут ограничивать соединения приложения только нужными сервисами.

## CSRF: запрос выполняет браузер пользователя

**CSRF (Cross-Site Request Forgery)** — ошибка, при которой посторонняя страница может заставить браузер пользователя выполнить нежелательное действие на другом сайте от его имени.

В схеме с сессионной cookie это может выглядеть так:

1. Пользователь уже вошёл в аккаунт магазина.
2. Он открывает постороннюю страницу.
3. Эта страница инициирует запрос к магазину с известными или предсказуемыми данными, например для смены почты.
4. Браузер прикладывает cookie магазина, если правила её отправки это допускают.
5. Если серверу достаточно этой cookie и действенная защита отсутствует, он может выполнить действие от имени пользователя.

### Что важно не путать

- Злоумышленнику не нужно красть или знать cookie: её прикладывает сам браузер.
- Cookie получает целевой сайт, а не злоумышленник.
- Перенаправление страницы необязательно: достаточно инициировать запрос. Например, обычная HTML-форма может отправить данные на другой сайт.
- Кража cookie с последующим использованием чужой сессии — захват сессии, а не CSRF.
- Cookie одного сервиса автоматически не даёт доступ к другим сайтам.
- Регулярная смена cookie сама по себе не устраняет CSRF: браузер может приложить действующее значение и к нежелательному запросу.

### Для чего нужен CSRF-токен

В распространённой схеме сервер создаёт секретный непредсказуемый токен и связывает его с сессией:

1. Сервер передаёт токен странице с формой.
2. Страница отправляет его вместе с запросом — например, отдельным полем формы или специальным заголовком.
3. Сервер проверяет наличие и правильность токена **до изменения данных**.
4. Если обязательный токен отсутствует или неверен, сервер отклоняет действие.

Ограничения браузера обычно мешают посторонней странице прочитать токен с другого сайта. Пользователь вручную его не вводит. Токен может выдаваться на сессию или на отдельный запрос.

### Для чего нужен SameSite

**SameSite** — атрибут cookie. Сервер задаёт его, а браузер по этому правилу решает, отправлять ли cookie в межсайтовом запросе. Решение зависит от значения атрибута и контекста запроса.

Если сессионная cookie не отправлена, в рассматриваемой схеме сервер не сможет определить вошедшего пользователя по ней. SameSite дополняет защиту от CSRF; проверку обязательного токена сервер всё равно должен выполнить до действия.

| Механизм | Его роль |
| --- | --- |
| Сессионная cookie | Позволяет серверу найти сессию пользователя. |
| CSRF-токен | Дополнительное значение, которое сервер проверяет для защищённого действия. |
| SameSite | Правило отправки cookie, которое применяет браузер. |

### Короткое сравнение

| Вопрос | SSRF | CSRF |
| --- | --- | --- |
| Кто отправляет запрос? | Сервер приложения. | Браузер пользователя. |
| Что пытаются вызвать? | Обращение сервера к непредусмотренному ресурсу. | Действие на сайте от имени пользователя. |

## Как описывать результат проверки

Сначала фиксируют то, что получилось наблюдать. Затем объясняют, какой вывод из этого следует и какие вопросы остались открытыми.

- **Наблюдение:** конкретный ответ сервера или проверенное изменение в приложении.
- **Вывод:** что это наблюдение позволяет установить.
- **Возможное последствие:** что ещё может произойти при дополнительных условиях.

Например, в условной задаче почта изменилась при ответе `403`. По условию действие не было предотвращено. Захват аккаунта — возможный дальнейший риск, если новый адрес позволяет восстановить пароль; его нельзя считать выполненным только по факту смены почты.

Для понятного отчёта достаточно ответить на несколько вопросов:

1. **Что проверялось?** Функция, стенд, роль пользователя и инструменты.
2. **Как повторить?** Шаги и необходимые условия.
3. **Что ожидалось?** Как приложение должно было обработать запрос.
4. **Что получилось?** Статус, тело ответа и проверенное состояние приложения.
5. **Что установлено?** Подтверждённый результат и границы проверки.
6. **Какой риск и что исправлять?** Возможные последствия, обоснованное исправление и способ его проверить.

В начале отчёта указывают, выполнена ли проверка на сайте или разбирается условная задача. Запросы, ответы и снимки экрана прикладывают, если они доступны. Пароли, значения сессий и токены в таких материалах скрывают с помощью `<REDACTED>`.
