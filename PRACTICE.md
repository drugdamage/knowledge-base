# Практика

## Burp Suite: повтор запроса проверки наличия товара

**Выполненная проверка** в учебном магазине PortSwigger Web Security Academy. Использовались Burp Suite Community Edition и встроенный Burp Browser.

### Что проверялось

Задача — найти запрос проверки наличия товара, отправить его через Repeater и прочитать ответ. В магазине использовался `POST /product/stock` с параметром `stockApi` в теле запроса.

### Шаги

1. Открыть страницу лаборатории, скопировать адрес магазина и открыть его в Burp Browser.
2. Выбрать товар и нажать **Check stock**.
3. В **Proxy → HTTP history** найти `POST /product/stock` и просмотреть его содержимое.
4. Нажать на запрос правой кнопкой мыши и выбрать **Send to Repeater**.
5. В **Repeater** нажать **Send**, без изменения данных запроса.
6. Во вкладке **Response** прочитать статус и тело ответа.

### Результат

Ожидалось получить сведения об остатке выбранного товара на складе.

| Что получено | Значение |
| --- | --- |
| HTTP-статус | `200 OK` |
| Тело ответа | `170` |

По смыслу функции число `170` интерпретируется как количество доступных единиц товара. В просмотренном ответе тело было отделено от заголовков пустой строкой.

### Что из этого следует

Обычный запрос найден и повторно отправлен через Repeater. Получен ответ `200 OK` с телом `170`.

**SSRF этой проверкой не подтверждена. Отсутствие уязвимости также не установлено.** Лаборатория SSRF не завершена. Внутренний адрес назначения и проверка allowlist отдельно не исследовались; по этому ответу нельзя достоверно определить внутренний маршрут запроса.

Результат записан вручную по выполненной проверке. Полный HTTP-экспорт и снимки экрана не приложены.

Материалы: [учебная лаборатория](https://portswigger.net/web-security/ssrf/lab-basic-ssrf-against-localhost), [Burp Repeater](https://portswigger.net/burp/documentation/desktop/tools/repeater).

## CSRF: разбор условной задачи

**Условная учебная задача. Практический тест на сайте не выполнялся.**

### Условие

По условию задачи:

1. Пользователь вошёл в аккаунт.
2. Для смены почты требуется CSRF-токен.
3. Отправлен запрос без обязательного токена.
4. Сервер вернул `403 Forbidden`.
5. После обновления страницы профиля в аккаунте отображается новая почта.

### Что должно было произойти

Сервер должен был отклонить запрос без обязательного токена **до изменения почты**. После обновления профиля должен был остаться прежний адрес.

### Что означает результат

По условию задачи почта изменилась, значит действие не было предотвращено. Ответ `403` сообщил об отказе, но фактическое состояние аккаунта ему не соответствует.

Задача показывает, почему нужно проверять и ответ сервера, и сохранённые данные. Она касается обработки обязательного токена. Межсайтовая отправка запроса через браузер пользователя отдельно не проверялась.

### Возможные последствия

Если через новый адрес можно восстановить пароль, такая смена почты может привести к захвату аккаунта. Это возможный риск, зависящий от других проверок сервиса; захват аккаунта в этой задаче не воспроизводился.

### Как должно работать исправление

Наличие и правильность CSRF-токена проверяются до записи новой почты. Если проверка не пройдена, сервер отклоняет действие, а прежний адрес остаётся в профиле.

Подробнее: [OWASP — проверка CSRF-токена](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#synchronizer-token-pattern).
